PROBLEM / WHY THIS SKILL02
先理解问题

NPU 空闲，不等于存储一定慢

NPU PRIMER

NPU 可以先理解成“计算设备”

它像 GPU 一样负责大量计算。训练时，CPU、DataLoader 和存储需要持续把数据送给它；没有数据可算时，它可能空闲。

STORAGEDATALOADERNPU
存储读取慢

本地盘、NFS 或远程元数据访问无法及时供数。

CPU 处理慢

例如图片解码繁忙，磁盘实际可能很空闲。

通信或算子问题

调度与任务下发

EVIDENCE MODEL / TWO CHAINS07
核心设计

两条证据链，不能混为一谈

① Host IO 压力链 R100 — R400

R100
本地块设备

吞吐、IOPS、await、队列是否持续承压。

R200
NFS 网络存储

当前窗口是否出现延迟、重传或超时。

R300
小文件与远程元数据

元数据操作延迟和 IO 粒度是否异常。

R400
多进程 IO 干扰

多个活跃 PID 是否争抢同一受压设备。

② NPU 传导链 R500

R500
HOST IO+NPU IDLE

必须属于同一 workload、同一目标设备，并且证据时间窗口真实重叠。

只有 Host IO 已确认，再看到可信的同窗 NPU 空闲证据，才能报告“存储可能导致 NPU 等待”。

R000证据质量底座：工具缺失、权限不足、格式错误或时间不重叠，都要降置信度，不能解释成“系统健康”。

规则详解 / 采集是否完整08
规则详解 01 / 06

R000：先判断证据够不够

R000

先检查信息有没有采全；信息不完整时，后面的结论就不能说得太确定。

采集什么 输入

  • 哪些信息完全没有采到。
  • 哪些信息只采到一部分，或者结果为空。
  • 哪些信息因为权限、命令或格式问题采集失败。
  • 这些状态统一记录在 Snapshot 的“采集情况”中。

怎么判断 判断

1
检查完全缺失

只要有信息没采到，就明确写出缺少什么。

2
检查信息不完整

只采到一点、空结果或当前系统不支持，都不能算完整成功。

3
检查采集失败

权限不足、命令失败或格式错误，会让相关结论降低可信度。

4
确认关键数据都采到了

只能说明“信息完整”，不能说明服务器没有性能问题。

得到什么 输出

信息级别提示
可信程度能明确知道哪些信息缺失
结论列出缺失、不完整和采集失败的信息。
判断依据Snapshot 中记录的采集状态。
最容易讲错的地方

R000 只能确定“哪些信息没采到”，不能证明服务器是健康的。

一句话R000 先检查信息是否完整：没采到，不等于没有问题。

规则详解 / 本地磁盘09
规则详解 02 / 06

R100：本地磁盘是否持续繁忙

R100

同时查看磁盘忙碌程度、请求等待、排队和读写速度，不会只看某一瞬间的峰值。

采集什么 输入

  • 磁盘有多忙，也就是忙碌时间占比。
  • 每秒读写多少数据、处理多少次读写请求。
  • 每次读写要等多久，以及有多少请求在排队。
  • 磁盘类型：机械硬盘、固态硬盘或未知设备。
  • 采集持续多久、有效样本有多少，以及可选的设备规格。

怎么判断 判断

1
先确认磁盘确实在读写

读写速度 ≥1 MB/s，或每秒读写请求 ≥100 次，排除磁盘几乎没工作的情况。

2
再看是否出现排队或等待

排队请求 ≥2，或等待达到参考线：机械盘 20ms、固态盘 5ms、未知设备 15ms。

3
确认持续繁忙

平均忙碌程度 ≥85%，至少有 3 个有效样本，同时存在排队、等待或接近设备性能上限。

4
证据不足就降低可信度

只有瞬间峰值，或者采集不到 10 秒，都不能直接判定为持续瓶颈。

得到什么 输出

检查对象检查了哪些磁盘，哪些磁盘持续繁忙。
繁忙程度持续异常 / 可能异常 / 短时峰值 / 正常
问题类型速度到顶 / 请求过多 / 排队等待
诊断结果严重程度、可信度和证据时间段
最容易讲错的地方

高速固态盘可以同时处理很多队列。即使看起来很忙，只要等待和排队正常，就不能直接判定磁盘是瓶颈。

高可信条件磁盘持续繁忙 + 确实有读写 + 出现排队或等待 + 有足够长的采集证据。

规则详解 / 网络存储10
规则详解 03 / 06

R200：网络文件盘是否真的变慢

R200

数据放在网络文件盘上，不代表它一定有问题；还要看到访问慢、重复发送或超时。

采集什么 输入

  • 数据路径是不是网络文件盘（NFS），连接的是哪台存储服务器。
  • 当前采集时间内一共发生了多少次访问。
  • 一次访问来回要多久，存储端处理要多久。
  • 请求重复发送了多少次，是否出现严重超时。
  • 这些数据是否属于目标训练任务，并且采集时间一致。

怎么判断 判断

1
确认是同一个网络文件盘

存储服务器、挂载位置和文件系统类型都要对应，不能只看路径名字相似。

2
只看本次采集期间的数据

历史累计数据、旧连接数据和其他任务的数据全部排除。

3
确认网络存储异常

访问次数 ≥200，且来回延迟 ≥50ms、处理时间 ≥100ms 或重复发送率 ≥1%；出现严重超时也算强信号。

4
时间对不上就降低可信度

挂载信息和性能数据不是同一时间采集的，就不能给出高可信结论。

得到什么 输出

检查对象发现了哪些网络文件盘，哪些已经确认异常。
任务范围目标数据路径是否覆盖，以及还缺什么信息。
诊断结果确认异常、可能异常，或者证据不足。
其他类型非 NFS 网络存储转交对应工具继续检查。
自动化范围

当前只有 NFS 可以自动深入判断。其他网络存储只能识别类型，并建议下一步使用什么工具检查。

证据不足只知道“数据在网络盘上”或“读取速度低”，都不能直接认定网络存储是瓶颈。

规则详解 / 远程文件访问11
规则详解 04 / 06

R300：大量小文件是否拖慢读取

R300

重点检查打开文件、查找文件和读取目录是否很慢，同时识别大量小文件读取特征。

采集什么 输入

  • 打开文件、查找文件、读取目录等操作发生了多少次。
  • 这些操作一次来回要多久，存储端处理要多久。
  • 每秒读取次数和读取速度，用来计算每次读取的数据大小。
  • 文件数量空间（inode）使用率，只作为辅助背景。
  • 是否属于目标网络文件盘，以及采集时间是否一致。

怎么判断 判断

1
确认找文件等操作很慢

相关操作 ≥50 次，并且平均来回延迟 ≥10ms 或处理时间 ≥20ms。

2
确认属于当前任务

必须对应目标网络文件盘，并且挂载信息和性能数据来自同一时间。

3
识别大量小文件特征

每秒读取 ≥5000 次，且每次平均读取 <16KB，只能判断为“可能存在小文件问题”。

4
文件数量空间只作参考

使用率 ≥80% 会提示，但不能单独证明读取慢。

得到什么 输出

确认问题哪些网络盘的找文件、开文件操作明显变慢。
可能问题哪些磁盘呈现大量小文件读取特征。
辅助背景哪些文件系统的文件数量空间使用较高。
缺少证据还需要哪些文件调用、缓存对照等信息。
最容易讲错的地方

每秒读取次数多、每次读取数据少，只能说明“像大量小文件”，不能直接证明找文件操作真的慢。

证据强弱找文件等操作的延迟是直接证据；小块读取是可能线索；文件数量空间只是背景。

规则详解 / 多进程争抢磁盘12
规则详解 05 / 06

R400：多个程序是否争抢同一磁盘

R400

多个程序都在读写还不够，还要证明它们同时使用同一块已经很忙的磁盘。

采集什么 输入

  • 每个程序（PID）正在访问哪些文件和磁盘。
  • 每个程序在当前时间内实际读写了多少数据。
  • R100 已经确认持续繁忙的磁盘。
  • 程序和磁盘的身份信息，避免把旧进程或同名设备认错。
  • 观察次数、共同时间段和目标数据路径。

怎么判断 判断

1
至少两个程序使用同一块磁盘

先排除内存文件系统、系统目录等不是真实数据盘的路径。

2
每个程序都要有完整证据

同一个程序必须既访问目标数据，又确实在读写，不能把两个程序的信息拼在一起。

3
这块磁盘本身必须已经很忙

多个程序共享一块空闲磁盘，不算造成性能问题的争抢。

4
确认是同一时间发生

至少观察 2 次，多个程序同时读写 ≥1 秒，并与磁盘繁忙时间重合。

得到什么 输出

高可信哪些程序正在争抢哪一块繁忙磁盘。
可能存在疑似争抢，但还有部分证据不完整。
证据较弱只看到共同访问，没有证明磁盘繁忙或同时读写。
缺少信息逐项说明哪一段证据还没有成立。
防误报设计

共同访问程序库、日志和系统文件，默认不算训练数据争抢；只重点检查目标数据路径。

高可信条件同一磁盘 + 每个程序都在真实读写 + 磁盘已经繁忙 + 至少同时持续 1 秒。

规则详解 / 是否影响 NPU13
规则详解 06 / 06

R500：服务器读写问题是否影响 NPU

R500

先确认目标训练任务确实存在存储问题，再判断这个问题发生时 NPU 是否也在等待。

采集什么 输入

  • R100—R400 已经确认的存储问题和发生时间。
  • 目标训练进程、数据路径和对应的磁盘或网络文件盘。
  • NPU 性能记录中，设备有多少时间处于空闲。
  • NPU 空闲时间和服务器存储异常时间是否重合。
  • 可选的前后对比实验，用来加强“存储影响 NPU”的判断。

怎么判断 判断

1
先确认服务器真的有存储问题

只接受 R100—R400 已经确认的问题，只有“可能异常”不能继续推断。

2
确认属于同一个任务和时间段

NPU 记录至少一半落在采集时间内，并与存储异常有共同时间段。

3
NPU 空闲比例 ≥10%

存储异常和 NPU 空闲同时发生时，报告“存储问题可能影响 NPU”。

4
存储正常就转查其他方向

继续检查 CPU 数据处理、任务调度、通信或算子计算问题。

得到什么 输出

发现关联报告“存储问题可能导致 NPU 等待”。
缺少信息列出缺少的 NPU 记录、任务身份或共同时间段。
转查方向CPU 数据处理 / 调度 / 通信 / 算子计算
结论边界当前最高只能说“可能影响”，不能直接证明因果。
不能作为正式证据

只看一次 NPU 利用率低，或者只看一份算子摘要，都不能证明存储导致了 NPU 空闲。

关联条件存储问题已确认 + 属于目标任务 + 时间真实重合 + NPU 空闲记录可信，缺一不可。

最后怎么讲

它能自动分析并给建议，执行权留给人

存储读取瓶颈

边界要主动说明

  • Profiler 摘要只能提供线索，不能伪造正式 NPU 空闲证据。
  • 自动给出建议，但系统变更由 Agent 或人工确认。
  • 不执行无法安全回滚的 drop_caches。
