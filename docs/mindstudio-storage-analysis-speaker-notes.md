# MindStudio Storage Analysis 讲稿

这份讲稿与 `mindstudio-storage-analysis-overview.html` 的 14 页顺序一致，可以直接照着念。

## 第 1 页：把“训练变慢”变成证据链

今天我介绍的是 MindStudio Storage Analysis Skill。

它不是让大模型看到几个指标以后猜“磁盘可能有问题”，而是把训练变慢这件事拆成一条可以复查的证据链。先采集服务器现场信息，再用固定规则判断，最后由 Agent 把结果解释成人能理解的结论和建议。

所以这套方案的核心分工是：程序负责采集事实和做稳定判断，Agent 负责理解问题、组织流程和解释结果。

## 第 2 页：为什么不能看到 NPU 空闲就怪存储

先说一个前提：NPU 空闲，不等于存储一定慢。

NPU 可以简单理解成负责计算的设备。训练时，服务器需要不断把数据准备好并送给 NPU。如果数据没及时到，NPU 就可能在等待。

但造成等待的原因不只有存储。也可能是 CPU 解码图片太慢、多卡通信有问题，或者任务没有及时下发。

所以这个 Skill 的定位很明确：它重点检查存储方向，判断本地磁盘、网络存储、远程文件访问或多个程序争抢磁盘，是否可能让 NPU 等数据。

## 第 3 页：整体主流程

整套流程一共有六个交接点。

第一步，Agent 理解用户问题并定位目标。用户已经给出训练进程编号和数据路径，就直接使用；没有给出时，先运行只读发现程序查找候选。候选不明确，才把最相关的几个选项交给用户确认。

第二步，采集程序只读检查服务器的磁盘、网络存储、进程和挂载信息。

第三步，把这些原始事实保存成 `io_snapshot.json`。它相当于一次现场检查记录。

第四步，分析程序读取这份记录，执行固定的 R000 到 R500 规则。

第五步，得到 `findings.json`，里面保存发现的问题、依据、可信度、缺失信息和建议。

最后一步，Agent 把这些结构化结果讲成人能理解的诊断结论，同时调用固定程序生成一份离线 HTML 报告。

## 第 4 页：前四个生产脚本

这里先看前四个生产脚本，它们负责产生诊断数据，而且职责不一样。

第一个是 `discover_io_target.py`，它是目标导航员。PID 或数据路径未知时，它只读查看进程启动命令、工作目录、打开文件和挂载关系，输出候选目标和推荐依据。如果几个候选很接近，它会明确要求用户确认，不会替用户猜。

第二个是 `collect_io_snapshot.py`，它是现场采集员。Agent 给它采集时长、已确认的进程编号和数据路径，它只读检查服务器，然后输出 `io_snapshot.json`。

第三个是 `analyze_io_snapshot.py`，它是规则裁判。它读取这份 Snapshot，再结合可选的正式 NPU 性能记录，执行 R000 到 R500，输出 `findings.json`。

第四个是 `summarize_msprof.py`，它是 NPU 侧的辅助观察员。它从 NPU 性能工具的算子记录里提取等待线索，但它不能单独证明 NPU 空闲，更不能单独证明存储是原因。

因此主诊断链是：发现并确认目标，采集 Snapshot，分析 Findings。NPU 摘要器只是辅助证据。下一页还有第五个生产脚本，专门负责把这些结果展示出来。

## 第 5 页：第五个脚本生成 HTML 报告

第五个生产脚本叫 `render_io_report.py`，它是报告生成员。

它读取前面脚本产生的目标候选、IO Snapshot、规则 Findings 和可选的 msprof 摘要。Agent 另外提供一个很小的 `agent_report.json`，里面只有通俗总结、建议、依据了哪些规则，以及当前还缺什么证据。

然后这个固定脚本负责生成图标、规则卡片和数据表格，最后输出一个 `io_report.html`。它只做展示，不会重新执行 R000 到 R500，也不会执行任何优化建议。

这里的关键点是：纯语言模型也可以完成。模型只需要读 JSON、写总结 JSON、调用脚本，不需要看截图，也不需要自己编写 HTML。多模态能力只在我们开发模板、检查视觉效果时有帮助，不是生产运行的要求。

最终用户会同时得到两份结果：终端里的简要诊断，以及浏览器可以直接打开的离线 HTML 报告。

## 第 6 页：io_snapshot.json 里有什么

`io_snapshot.json` 不是结论，它是一张服务器的现场检查记录。

它先记录目标和时间：检查的是哪个训练进程、哪个数据路径、什么时间采集。

然后记录本地磁盘的情况，例如磁盘有多忙、读写速度、每次读写等待多久、有没有请求排队。

如果数据在网络文件盘上，它还会记录 NFS 是否挂载、访问是否变慢、是否重复发送或超时。

它还记录哪些程序正在读写、这些程序最终访问到哪块磁盘；同时保存磁盘空间、内存缓存等背景信息。

最后，它会明确记录哪些信息没有采到、哪些因为权限或命令失败而不可用。这个部分很重要，因为没有采到数据，不代表系统没有问题。

## 第 7 页：两条证据链

这套设计最关键的地方，是把两件事分成两条证据链。

第一条是服务器存储压力链，也就是 R100 到 R400。它分别检查本地磁盘是否持续繁忙、网络文件盘是否变慢、大量小文件是否拖慢读取，以及多个程序是否在争抢同一块磁盘。

第二条是 NPU 传导链，也就是 R500。它不重新猜存储问题，而是检查已经确认的存储问题，是否和目标任务的 NPU 空闲发生在同一时间。

只有这两条链都成立，才能说“存储问题可能让 NPU 在等数据”。如果只看到磁盘忙，或者只看到 NPU 空闲，都不能直接把两者连成因果。

另外，R000 是所有规则的底座。工具缺失、权限不足或时间对不上，都必须降低结论可信度。

## 第 8 页：R000，信息是否采全

R000 不判断磁盘快不快，它只回答一个问题：我们拿到的信息够不够。

它会检查三类情况：有没有完全没采到的信息，有没有只采到一部分的信息，以及有没有因为权限、命令或格式问题而采集失败。

如果关键数据缺失，后面的规则仍然可以给出线索，但不能把结论说得太确定。

所以 R000 的价值是防止一个常见错误：把“没有发现问题”误解成“系统没有问题”。有可能只是我们没有采到对应证据。

## 第 9 页：R100，本地磁盘是否持续繁忙

R100 检查服务器自己的磁盘是否一直很忙，已经影响读数据。

它不会只看某一瞬间磁盘利用率很高，而是同时看：磁盘是否真的在读写、读写请求是否在排队、每次请求是否等待太久，以及这种情况是否持续了一段时间。

比如，平均忙碌程度很高，同时有排队或等待，并且采集到了足够长的连续数据，才会认为本地磁盘持续繁忙。

如果只是偶尔出现一个峰值，或者采集时间太短，结论就会降低可信度。

最后它会输出：哪些磁盘有问题、是读写速度到顶、请求太多，还是排队等待造成的。

## 第 10 页：R200，网络文件盘是否真的变慢

R200 重点检查 NFS，也就是数据放在另一台存储服务器上、通过网络访问的场景。

仅仅知道数据路径挂在网络文件盘上，并不能说明网络存储就是瓶颈。我们还要确认这是不是目标任务正在使用的那一个网络文件盘，并且只看本次采集时间内发生的访问。

当访问次数足够多，同时出现访问来回延迟高、存储端处理慢、重复发送或严重超时时，才能确认网络文件盘存在异常。

如果挂载信息和性能信息不是同一时间采集的，或者对应不上同一个存储服务器，结论就不能给得太高。

当前这套 Skill 对 NFS 有专门规则；其他网络存储类型会识别出来，并交给对应工具继续检查。

## 第 11 页：R300，大量小文件是否拖慢读取

R300 关注的是另一类很常见的问题：数据可能不是大文件顺序读取，而是需要频繁打开文件、查找文件和读取目录。

例如一个数据集里有海量小文件，真正慢的地方可能不是读文件内容，而是不断“找文件、开文件”。

这个规则会直接看这些操作是否发生很多次、每次花多久。如果找文件和开文件的延迟明显升高，就可以确认远程文件访问变慢。

它也会看每秒读取次数是否很高、每次读取数据是否很小。

举个例子，同样读取大约 1GB 数据：如果读取的是大文件，可能只需要读 100 次，每次读大约 10MB；如果读取的是大量小文件，可能需要读 10 万次，每次只读大约 10KB。第二种方式会多出大量找文件、打开文件和关闭文件的操作，所以更容易拖慢数据准备。

但是，“读取次数很多、每次读取很小”只能说明它看起来像大量小文件。也有可能是程序主动把一个大文件分成很多小块读取。因此这只能作为线索，还需要结合找文件、打开文件等操作的延迟，才能进一步确认根因。

文件数量空间使用率高也只是背景信息，不能直接说明读取慢。

## 第 12 页：R400，多个程序是否争抢同一块磁盘

R400 检查多个程序是否在争抢同一块已经很忙的磁盘。

只看到多个程序都在读写，不够。每个程序都要证明自己访问的是目标数据，并且在当前时间内确实在读写。

同时，它们必须使用同一块磁盘，而且这块磁盘已经被 R100 确认为持续繁忙。

最后还要检查时间：这些程序是不是至少有一秒钟同时在读写，和磁盘繁忙时间是不是重合。

这样做是为了避免误报。比如多个程序同时访问日志、程序库或系统文件，并不等于它们在争抢训练数据。

## 第 13 页：R500，存储问题是否可能影响 NPU

R500 是最后一步，它回答的是：已经确认的服务器存储问题，是否可能让 NPU 等数据。

首先，R100 到 R400 里必须已经确认存在存储问题；仅仅“可能异常”不能继续往下推断。

然后要确认这是同一个训练任务，数据路径和设备能对上，而且存储异常发生的时间和 NPU 空闲时间真实重合。

如果存储异常发生时，NPU 空闲比例也达到一定程度，就可以报告“存储问题可能影响 NPU”。

这里要特别注意措辞：当前结论是“可能影响”，不是直接证明因果。因为 NPU 空闲也可能来自 CPU 数据处理、任务调度、通信或算子计算。

## 第 14 页：能力边界和最后结论

最后总结一下。

这个 Skill 能自动分析四类存储问题：本地磁盘读取瓶颈、NFS 网络存储异常、远程文件和小文件访问慢，以及多个程序之间的磁盘争抢。

它会给出带证据和可信度的结论，也会给出下一步建议。但它不会自动修改服务器配置，执行权仍然留给 Agent 或人工确认。

诊断结束后，它既在终端返回简要结论，也生成一份包含表格、规则依据和 Agent 建议的离线 HTML，方便查看和交付。

它的边界也要主动说明：目前网络存储的深入自动分析主要支持 NFS；NPU 摘要只能提供线索；没有足够的 NPU 和时间重合证据时，不能把存储问题直接说成 NPU 利用率低的唯一原因。

一句话概括这套设计：Agent 负责理解和解释，程序负责发现目标、采集和判断；先找准任务，再证明存储问题存在，最后判断它是否可能影响 NPU。
