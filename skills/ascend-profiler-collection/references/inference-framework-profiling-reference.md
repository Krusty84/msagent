# 未适配 `torch.profiler` 的推理框架适配参考

适用场景：

- 推理逻辑封装在服务框架或推理引擎中
- 需要在框架内部真实执行路径上注入 `torch_npu.profiler`
- 在线服务和离线推理都适用

本参考文档不单独定义新的 `torch_npu.profiler` 骨架，统一复用主文档分支 B。

## 1. 定位注入点

只做三件事：

1. 找到真实模型执行路径，而不是停留在启动命令、服务入口或调度层
2. 找到真正触发 NPU 计算的进程，而不是只看主控或调度进程
3. 把注入点放在最薄的执行包装层，确保能稳定覆盖真实请求

判断标准：

- `start` 放在目标请求进入真实执行前
- `step` 放在最小重复单元完成后；没有稳定循环时可以不调用
- `stop` 放在目标请求执行结束后

## 2. 触发采集

在线服务：

- 先确认服务 ready
- 再发送 1 到 2 条真实请求
- 不要把“服务启动成功”误判为已经完成采集

离线推理：

- 确认真正执行了一次 `generate`、batch 推理或真实 `forward`
- 不要把参数解析、模型构建或 warmup 当成采集目标

## 3. 额外注意

- 多进程场景下，profiler 配置必须传到真实执行进程
- 如果框架内部还有外部推理后端，注入点和配置都要透传到后端
- 通用的产物验证、故障排查和恢复流程，统一参考 [../SKILL.md](../SKILL.md)
