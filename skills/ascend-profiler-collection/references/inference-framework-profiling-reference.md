# 推理框架 Profiling 参考

本参考文档对应 `ascend-profiler-collection` 的分支 C，适用于以下场景：

- 用户没有可直接编辑的 `.py` 或 `.sh`
- 推理逻辑封装在服务框架或推理引擎中
- 需要在框架内部的真实执行路径上注入 `torch_npu.profiler`
- 既要支持在线服务拉起，也要支持离线推理拉起

分支 C 不单独定义新的 `torch_npu.profiler` 构造模板，统一复用主文档中的公共骨架；本分支只决定注入点、进程归属，以及 `start / step / stop` 如何贴合真实推理执行路径。

## 1. 定位注入点

目标是找到真实模型计算的执行边界，而不是停留在启动命令、外层服务入口或离线脚本入口。

建议按以下顺序定位：

1. 先把一次在线请求从入口到模型执行的主链路串出来。
2. 先排除肯定不适合注入的位置，例如服务入口层、调度层、只做参数整理的 CPU 包装层。
3. 找到请求级执行汇合点。这个位置要同时满足两个条件：
   - 足够靠下，已经进入模型执行阶段；
   - 足够靠上，能够覆盖大多数真实请求。
4. 继续向下确认该位置是否真的触发了设备计算。
5. 最终注入点应尽量选择最薄的一层包装，内部直接调用原有前向或模型执行逻辑。

## 2. 经验规则

1. 在线服务场景中，负责采集 profiler 的进程不能只是调度进程，必须是真正执行模型计算的进程。
2. 注入 profiler 的位置必须位于真实 NPU 执行路径上，而不是只落在服务入口、调度层或纯 CPU 包装层。
3. profiler 的关键参数应统一复用主文档中的公共骨架，并支持由外部配置控制实际采集行为。
4. 优先构建统一的 Profiler 抽象层，收敛所有采集入口；各注入点应依赖统一的 `step()` 接口触发采集。

## 3. 在线与离线场景的拉起与触发

在线服务场景：

- 先确认服务已 ready，再发送请求。
- 典型检查包括端口监听、健康检查接口和日志中无 startup error。
- 再发送 1 到 2 条真实推理请求，确保请求真正进入模型执行路径，而不是只有服务启动、没有实际 inference step。

离线推理场景：

- 先确认离线脚本、CLI 或 SDK 调用会真实触发一次完整推理，而不是只做参数解析、模型构建或 warmup。
- 常见触发方式包括执行一次 `generate`、一次 batch 推理、一次评测样本推理，或一次真实 `forward/step`。
- 如果离线框架内部区分 warmup 和正式执行，优先确认 profiler 注入点能够覆盖两者，或者至少明确本次采集只覆盖其中哪一段。

通用要求：

- 只把“真实进入模型执行路径”的那次运行视为采集目标。
- 不要把“服务成功启动”或“脚本成功拉起”误判为 profiling 已经触发完成。
