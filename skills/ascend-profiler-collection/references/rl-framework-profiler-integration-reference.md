# 强化学习框架 Profiling 参考

本参考文档对应 `ascend-profiler-collection` 的分支 D，适用于强化学习训练框架。

分支 D 不单独定义新的 `torch_npu.profiler` 构造模板，统一复用主文档中的公共骨架；本分支只决定训练主控层、执行层、最小重复单元，以及 `start / step / stop` 如何贴合真实训练语义。

## 1. 定位注入点

### 1.1 识别训练主控流程

先定位是谁在驱动整个训练过程，重点关注：

- 谁负责 `epoch` 或 `step` 的推进
- 谁负责训练、验证、保存、日志等主流程控制
- 一次“训练步”在框架中是如何定义的

目标是确认：

> 训练区间的开始和结束由哪里控制。

### 1.2 识别训练执行层

继续沿训练调用链向下定位，找到真正执行前向、反向和优化更新的位置，重点看：

- 哪一层真正处理训练 batch
- 哪一层负责把任务分发到 `worker`、`executor` 或 `engine`
- 哪一层最接近实际计算过程

目标是确认：

> 训练不是由谁发起，而是由谁真正执行。

### 1.3 识别最小重复执行单元

Profiler 的 `step` 应与最稳定的重复单元对齐，因此需要继续确认：

- 一个 batch 是否会再拆成多个 `mini-batch`
- 一个训练 step 是否会再拆成多个 `micro-step`
- 哪个循环最贴近真实计算节奏

目标是确认：

> 每次推进 profiler 的最佳时机在哪里。

### 1.4 找统一的 profiler 封装层

不要直接把 profiler API 散落到业务逻辑里。优先确认框架内是否已有统一抽象：

- 是否存在统一的 profiling 开关或调度入口
- 是否有按工具类型分发的封装层
- 是否支持不同后端共用一套生命周期

目标是确认：

> 注入点应该接在统一能力层，而不是散落在业务代码里。

### 1.5 决定 `start / step / stop` 的位置

按职责拆开处理：

- `start` 放在目标训练区间开始前
- `step` 放在最小重复执行单元完成后
- `stop` 放在目标训练区间结束后

判定原则：

- 必须稳定经过
- 必须频率明确
- 必须和训练语义对齐
- 不能依赖偶发分支
- 不能放在纯日志、纯配置或纯保存逻辑里

### 1.6 验证注入点是否合理

至少检查以下问题：

- 采集是否覆盖目标训练区间
- `step` 是否会少调或多调
- 多角色或多 worker 场景下是否时序一致
- profiler 生命周期是否闭环
- 不同后端是否仍能复用同一套调度逻辑

## 2. 输出建议

最终输出建议至少包含以下 4 项：

- 训练主控层在哪里
- 执行层在哪里
- 最小重复单元在哪里
- `start / step / stop` 分别应该注入到哪一层

## 3. 经验规则

- 主控层适合放区间级控制
- 执行层适合放细粒度推进
- `step` 优先和 `mini-batch` 或 `micro-step` 对齐
- 统一封装优先于直接接入底层 API，并应复用主文档中的公共 `torch_npu.profiler` 骨架
- 先保证触发时机正确，再考虑采集内容和性能开销
